## Part 1 — Storing and retrieving data: CSV vs Parquet

### Research

* **CSV** is a row-oriented, uncompressed text format. Every read must parse every
  byte of every line (including type inference for strings), and writes have no
  built-in compression. It is human-readable and universally supported.
* **Parquet** (Apache Arrow ecosystem, `pyarrow`) is a **column-oriented, binary**
  format with per-column encoding (dictionary, RLE) and built-in compression
  codecs. Reads decode only the bytes you need, and I/O is minimized because the
  files are far smaller. Parquet also stores a schema, so no type inference is done
  at read time.

Compression schemes tested (all supported natively by PyArrow):

| Codec | Trade-off |
|-------|-----------|
| `snappy` | default; extremely fast, decent ratio |
| `zstd`  | strong ratio, very fast decompression |
| `gzip`  | slightly stronger ratio, slowest (used at level 1 to keep it realistic) |

### Methodology

For each scale (1x = 619,040 rows, 10x = 6,190,400 rows, 100x = 61,904,000 rows) the
script measures:

1. **Write time** — CSV via pandas `to_csv` (append mode); Parquet via
   `pyarrow.parquet.ParquetWriter` appending row groups (both approaches keep memory
   constant, so the comparison is fair).
2. **File size** on disk.
3. **Read time** — full-file load into memory with pandas (plus polars reads as an
   extra data point).

### Results

MacBook Pro (Apple silicon, 16 GB RAM, 10 cores), Python 3.13, pandas 3.1 / pyarrow / polars 2.1:

| Scale | Rows | Format | Size (MB) | Write (s) | Read (s, pandas) | Read (s, polars) |
|-------|------|--------|----------:|----------:|-----------------:|-----------------:|
| 1x    | 619,040   | CSV            | 29.6  | 0.58  | 0.096  | 0.014 |
|       |           | Parquet snappy | 10.3  | 0.059 | 0.0061 | — |
|       |           | Parquet zstd   | **8.5** | **0.064** | **0.0067** | 0.016 |
|       |           | Parquet gzip   | 8.6   | 0.15  | 0.014  | — |
| 10x   | 6,190,400  | CSV            | 295.8 | 5.98  | 1.06   | 0.18 |
|       |           | Parquet snappy | 102.6 | 0.60  | 0.061  | — |
|       |           | Parquet zstd   | **85.0** | 0.68  | **0.042** | 0.074 |
|       |           | Parquet gzip   | 86.3  | 2.21  | 0.077  | — |
| 100x  | 61,904,000 | CSV            | 2,958.1 | 60.9 | 10.3  | 2.24 |
|       |           | Parquet snappy | 1,026.5 | 5.87 | 1.29 | — |
|       |           | Parquet zstd   | **849.7** | 6.62 | 1.16 | **0.69** |
|       |           | Parquet gzip   | 863.5  | 15.7 | 0.96  | — |

Charts: `benchmarks/part1_charts.png`.

### Recommendation

* **At 1x** CSV is perfectly usable (sub-second reads, human-readable) — there is no
  *need* to convert, but Parquet/zstd already costs nothing and saves 3.5x disk.
* **At 10x** Parquet's advantages become obvious: ~9x faster writes, ~15-25x faster
  reads and 3.5x less storage.
* **At 100x** Parquet is essentially mandatory: writing CSV takes ~61 s vs ~6.6 s
  for Parquet/zstd; reading the CSV with pandas takes ~10 s vs ~1.2 s for Parquet
  (polars brings Parquet reads down to ~0.7 s), and the file shrinks from ~3.0 GB
  to ~0.85 GB.

**Final choice:** store the dataset as **Parquet with `zstd` compression** for all
analytics work (best size/speed balance in this benchmark — snappy is a touch faster
to write but zstd is smaller with equivalent read speed and even faster decompression
on large files). Keep the original CSV only as the ingestion/source format. When the
data grows to 10x/100x, the Parquet files can be read selectively (column projection
and predicate pushdown) which CSV cannot do at all.

## Part 2 — Pandas vs Polars, indicators and prediction models

### Research: why compare these two libraries

* **Pandas** is the most widely used DataFrame library. Operations are NumPy-backed
  but many per-group operations fall back to Python-level loops (e.g. `groupby(...)
  .transform(lambda ...)`), which do not scale well.
* **Polars** is a Rust-based DataFrame engine with a lazy query optimizer,
  vectorized kernels and true multithreading. Its expression API
  (`pl.col("close").rolling_mean(10).over("name")`) compiles to a single optimized
  plan instead of 505 Python callbacks.

For a 619k-row dataset either library works, but the benchmark below shows the gap
grows quickly with scale, which matters given the 10x/100x growth assumption of the
assignment.

### Technical indicators added (per ticker)

| Indicator | Formula | Rationale |
|-----------|---------|-----------|
| SMA(10) | 10-day simple moving average of close | Trend direction |
| MACD(12,26,9) | EMA12 − EMA26, with 9-day signal line + histogram | Momentum / trend changes |
| RSI(14) | Wilder's relative strength index of daily gains/losses | Overbought/oversold |

Plus a **1-day return** column. To make the forecast a true *next-day*
prediction, **every feature is lagged by one day**: the models see only
information available at the close of day t−1 (yesterday's OHLC, volume,
indicators, close and return) to predict the close of day t — no look-ahead
leakage. All indicators are computed identically in pandas and polars and
the two engines were verified to agree to ~1e-4 (float32 rounding).

### Pandas vs Polars benchmark (619,040 rows)

| Stage | pandas (s) | polars (s) | Speedup |
|-------|-----------:|-----------:|--------:|
| Load CSV | 0.103 | 0.018 | 5.7x |
| 3 indicators (SMA/MACD/RSI) | 0.143 | 0.026 | 5.4x |
| Lag features + cleanup | 0.031 | 0.010 | 3.1x |
| **Total data prep** | **0.277** | **0.054** | **5.1x** |

Chart: `benchmarks/part2_charts.png`. The final NumPy matrices fed to scikit-learn
were verified to be identical between the two engines (max deviation ~1e-4, i.e.
float32 rounding). Model training itself is engine-independent: LinearRegression
0.04 s, Random Forest 67 s.

### Prediction models (80/20 chronological backtesting)

Two algorithms predict the **next-day closing price** for all 505 companies.
Both are trained on the **one-day log-return** (standard practice for prices:
stationary, comparable across tickers, avoids heteroscedasticity), and the dollar
forecast is recovered as `close(t-1) × exp(ŕ)`:

1. **Linear Regression** (with `StandardScaler`) — simple, fast, interpretable
   baseline that extrapolates gracefully in price space.
2. **Random Forest** (120 trees, `max_depth=20`, `min_samples_leaf=5`) — captures
   non-linear interactions between lagged prices and indicators.

The split is **chronological**: rows are sorted by date and the first 80% of trading
days train the models, the last 20% backtest them (no shuffling → no look-ahead
leakage). Features (all lagged one day): `open_l1, high_l1, low_l1, volume_l1,
sma10_l1, macd_l1, macd_signal_l1, rsi_l1, close_l1, ret1_l1`.

### Model results (test period, all companies)

| Model | Overall RMSE ($) | Overall MAE ($) | Overall R² | Median per-ticker RMSE ($) | Tickers where it wins (lower RMSE) |
|-------|-----------------:|----------------:|-----------:|---------------------------:|-----------------------------------:|
| Linear Regression | **2.241** | **0.908** | 0.99969 | 0.950 | 335 / 505 |
| Random Forest     | 2.260 | 0.912 | 0.99969 | 0.951 | 170 / 505 |

Metrics are in dollars after back-transforming the log-return predictions.
Train rows 486,870 (through 2017-02-10), test rows 125,093 (2017-02-13 → 2018-02-07).

**Feature importance (Random Forest, top 5):** `ret1_l1` 0.18, `volume_l1` 0.15,
`rsi_l1` 0.14, `macd_signal_l1` 0.14, `macd_l1` 0.13 — yesterday's return, volume
and momentum indicators carry the signal, which is consistent with the near
random-walk behaviour of daily prices.

### Conclusion of Part 2

* **Polars is the better engine for this workload.** It produced *bit-identical*
  results ~5x faster with far less code (a single expression per indicator vs
  pandas `groupby(...).transform(lambda ...)` Python callbacks). The gap grows with
  data size, so for the 10x/100x scale-up polars is the clear choice.
* **Both models are nearly tied** at ~0.9997 R² — next-day close is overwhelmingly
  determined by today's close. Linear Regression wins outright on 335/505 tickers,
  trains in 0.04 s (vs 67 s for the forest) and extrapolates safely when a stock
  trades outside its training price range (Priceline/PCLN at ~$1,880 grew ~20%
  beyond its training maximum — an early dollar-target experiment showed Random
  Forest RMSE of $255 vs $26 for LR there, because tree leaves cannot extrapolate).
* **Design decision:** models predict the **1-day log-return**, and the dollar
  forecast is `close(t-1) × exp(ŕ)`. This is standard for price series: returns are
  stationary and comparable across tickers, and it prevents the heteroscedastic
  blow-up above.
* **Recommendation:** Linear Regression (scaled, log-return target) as the primary
  model for this dataset — comparable accuracy, 1,500x cheaper to train, fully
  interpretable coefficients; Random Forest remains a strong secondary model and
  would pull ahead if non-linear features (e.g. sector data, sentiment) were added.

## Part 3 — Visual dashboard

### Research: dashboard libraries

| Library | Model | Strengths | Weaknesses |
|---------|-------|-----------|------------|
| **Streamlit** | plain Python script, top-down rerun | fastest to build, `@st.cache_data` caching, native Plotly, free Community Cloud hosting | limited fine-grained interactivity |
| **Dash** | Flask + React callbacks | full Plotly ecosystem, production-grade | callbacks add boilerplate; steeper learning curve |
| **Reflex** | Python compiled to React | very flexible components | younger ecosystem, more setup |

**Choice: Streamlit.** The assignment needs a ticker-searchable page with a handful
of linked charts; Streamlit delivers that in the least code with built-in caching
for the 30 MB CSV, and the app can be verified with a single command.

### What the dashboard shows

* Sidebar: ticker **search + select** (all 505 companies available) and model choice.
* Metric cards: per-ticker **RMSE / MAE / R²** on the test period and the
  **next-day price forecast** from both models.
* Charts: full price history with **SMA(10), MACD and RSI(14)** panels; the backtest
  window (actual vs predicted close); predicted-vs-actual scatter and error
  histogram; a raw data table.

Screenshots of the running dashboard are in `docs/screenshots/` and assembled into
`docs/CSIS4260_Assignment1_Dashboard_Screenshots.pptx`.
